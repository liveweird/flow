# Sample data — synthetic Jira Cloud dataset + WireMock stub

> The GitLab counterpart (`gitlab/generate.mjs`, a self-managed GitLab world and its stub) is documented in the last section, "GitLab stub".

This directory holds a **deterministic, zero-dependency** synthetic Jira Cloud dataset and the
WireMock stub that serves it, generated by `jira/generate.mjs`. It exists so that:

- `docker compose up` gives you a Jira-shaped API to point a real connection at without touching
  the real Atlassian cloud (`jira-stub` in `docker-compose.yaml`, `127.0.0.1:8094`);
- the server's integration tests (Testcontainers + the in-JVM WireMock `JiraStubServer`, which
  serves this dataset to the Jira client and sync pipeline) get a fixed, richly-shaped dataset to assert
  exact counts against (`jira/expected.json`), instead of hand-authored fixtures that drift from
  what the real API actually returns.

## Regenerating

```
node sample-data/jira/generate.mjs [--scale N] [--out DIR]
```

Node ≥24, no npm install. With **neither flag**, the script is **fully deterministic**: every
random draw comes from a seeded PRNG (mulberry32, fixed seed) and the "current time" is a frozen
constant (`2026-09-01T00:00:00.000Z`, never `Date.now()`) — running it twice produces
byte-identical output in `jira-stub/` and `jira/expected.json`. Verified as part of this commit;
re-verify after any change to the generator:

```
node sample-data/jira/generate.mjs && cp -r sample-data/jira-stub /tmp/a && cp sample-data/jira/expected.json /tmp/a/
node sample-data/jira/generate.mjs && cp -r sample-data/jira-stub /tmp/b && cp sample-data/jira/expected.json /tmp/b/
diff -rq /tmp/a /tmp/b   # must print nothing
```

Re-run it whenever you change the generator, and commit both `jira-stub/` and `jira/expected.json`
— they are build artifacts of `generate.mjs`, not hand-edited.

**`--scale N`** multiplies every project's issue/epic counts by `N` (default 1 — the committed
dataset's own shape, ~1,200 in-scope issues; `N=20` is the phase-3 performance run's ~24k-issue
dataset, `.claude/docs/ingestion.md`'s perf check). It never touches sprint/user/team counts, ids,
chunking or the day2 scenario at the default `N=1` (`Math.round(x*1) === x` is a no-op).
**`--out DIR`** writes to `DIR/jira-stub` and `DIR/jira/expected.json` instead of this directory —
used by the scale-20 performance run so it never touches the committed dataset:

```
node sample-data/jira/generate.mjs --scale 20 --out /tmp/flow-jira-x20
```

Runs with either flag are not asserted byte-identical against anything (only the default,
no-flags invocation is); they still draw from the same deterministic PRNGs.

### Phase 3 (v0.3.0) additions

On top of the phase-2 shape described below, the generator also produces the inputs the `metrics`
layer (`.claude/docs/domain-model.md`) needs, added by a **second, independently-seeded PRNG
stream** (`rng2`, distinct from the phase-2 dataset's own `rng`) so none of phase-2's ids,
timelines, the omitted bulkfetch chunk or the day2 scenario shift:

- **Epic story points** (D7) — every epic (in and out of scope) carries its own `customfield_10016`
  value, 20–80.
- **Epic dates** — a "Start date" custom field (`customfield_10015`, `schema.custom`
  `…:datepicker`) and the system `duedate` field on every epic; ~25% of epics get one later date
  change in the changelog (`fieldId: "duedate"` or `customfield_10015`, picked per epic).
- **Parent moves** — ~3% of tasks/stories/bugs parented to an epic move to a different epic in the
  same project once, as a `{field: "Parent", fieldId: "parent"}` changelog item; the issue's
  current `fields.parent` always reflects the last move's target (`expected.json` →
  `parentMoves`).
- **Story-point changes after start** — on Scrum stories that have started (passed their first
  In Progress transition): ~15% get a story-point value change dated after that transition; a
  further ~5% are "estimated late" (no story points at the start, gaining their eventual value only
  via that later changelog entry) — see `expected.json` → `estimates.taskEstimateChangedAfterStartCount`/
  `taskEstimatedLateCount`. Both are counted against each story's FINAL done_at (domain-model A35): a change or a "late" estimate
  that lands AFTER the story was done is a backfill, not an adjustment, so those cohort members moved out of the two counts into
  `taskEstimatedLateBecameAfterDoneCount` / `taskEstimateChangedAfterDoneCount`. A small **after-done backfill cohort** (~4% of the
  done stories with no adjustment, drawn from its own third PRNG stream `rng3`, run after the future-sprint placement so no `rng2`
  draw shifts) gets its eventual story points only 1–30 days after it was done: `taskEstimateBackfillCohortCount`, and
  `taskEstimatedAfterDoneCount` = the cohort + the late members that landed after done. Only the changelog histories grow
  (`changelog.inScopeHistories`/`allProjectsHistories`, +9); no issue, id, golden fixture or roster moves.
- **Work category** (`customfield_10030`, `schema.custom` `…:select`, options "Product
  Development"/"Maintenance"/"Cost of Poor Quality") — every epic, and ~60% of every other issue
  (D8's task-else-epic fallback needs both populated).
- **Worklog `created`/`updated` skew** — ~20% of worklogs get `created` = `started` + 1–5 days
  (instead of `created == started`); a further, independent ~10% get `updated` set later than
  `created` (report 14's late-logging measure).
- **Sprint `completeDate` skew** — ~30% of closed sprints get `completeDate` = `endDate` + 0–2 days
  instead of exactly `endDate`.
- **A future-sprint backlog** — ~10 estimated Scrum stories are placed (or reset, if not already
  never-started — see the code comment in `generate.mjs`) into their project's one future sprint,
  as a never-started TODO issue: D9's "future sprints count as backlog too" case, as opposed to a
  genuinely unscheduled backlog item.
- **A deterministic 30-user roster** over the 4 Atlassian Teams (2 users left on no team),
  `expected.json` → `teams.roster` — the source data for D1's dated team membership, entered by hand through the
  memberships API (phase-3 plan §2 decision 6) or seeded from the issues' Team field (the "Seed from Jira Team field"
  dialog; note the stub assigns the Team field to issues at random, independent of this roster).
- **Two golden fixtures**, computed by the generator from its own simulated timeline (never
  hand-authored) — `expected.json` → `golden.sprint` (one closed FLO sprint's committed/added/
  removed/final/delivered/carried-over/dropped MD and item counts, grace 0, 1 SP = 1 MD) and
  `golden.epic` (one FLO epic's own budget, start/due dates and child-SP sum) — the same
  "independent second implementation" precedent as `EXPECTED_STATUS_CATEGORY`
  (`.claude/docs/testing.md`), for a later commit's derivation-kernel tests to compare against.

These additions grow `changelog.inScopeHistories`/`allProjectsHistories` (new changelog entries)
but leave every other phase-2 figure — issue ids and counts, the omitted bulkfetch chunk, the day2
scenario, `worklogs.inScopeCount`/`inScopeIssueCount`, `reopens`, `sprints.carryOverCount` — bit
for bit unchanged (phase-3 plan §0 A2).

### A31 addition (v0.4.0) — one issue above the epic level

`generate.mjs` appends **one level-2 "Program" issue** (issue type `10010`, `hierarchyLevel: 2`, a Premium-style type above
the epic) to FLO, as the very last step before the stub files are written. It consumes neither PRNG, takes the next free
id and FLO key (`expected.json` → `aboveEpic.issueId`/`issueKey`), and is absent from every random loop (work category,
worklog skew, future-sprint candidates, day-2 candidates), so no pre-existing id, timeline, the omitted bulkfetch chunk, the
day2 scenario or the golden fixtures move. Only the counts it joins move, each by one (or, for the chunk count, to a new last
chunk): `issues.totalInScope`, FLO's `perProject` count, `worklogs.inScopeCount`/`inScopeIssueCount` and the whole-dataset worklog
counts, `changelog.bulkfetchChunkCount` (25: the 1,201st id opens a one-id chunk) and `mappingCount`. Its values are constants: To Do, no assignee, sprint or flag, 100 SP, ONE worklog
(id `790000`, `USERS[0]`, 4 h) and it is the `parent` of the two highest-id FLO epics other than the golden one
(`aboveEpic.childEpicIssueKeys`). `project/FLO/statuses` gains a Program row; `projects/fields` is unchanged (a field scheme
has no row for the type). What Flow must make of it — no task/epic/bridge row of its own, its worklog kept but never attributed
to an epic — is domain-model A31; `MetricsHierarchyLevelTest` and `ReportDataQualityTest` read it through
`expected.json` → `aboveEpic`. The data-profile FLO × Program workflow row is in `DataProfileTest`.

## The dataset

Four Jira projects the sample connection's `projectKeys` cover, plus a fifth that is deliberately
**out of scope** (to test that the client never requests its issues, yet still has to filter its
worklogs out of the instance-wide worklog feed — see "A1" in the ingestion plan):

| Key | Name | Board | In scope | Workflow | Issues |
|---|---|---|---|---|---|
| `FLO` | Flow Core | Scrum | yes | To Do → In Progress → In Review → Done | 401 (400 + the A31 Program) |
| `PLT` | Platform | Scrum | yes | To Do → In Progress → **Blocked** → In Review → Done | 350 |
| `GTM` | Go To Market | Scrum | yes | To Do → In Progress → In Review → **Waiting** → Done | 300 |
| `OPS` | Operations | Kanban | yes | To Do → In Progress → Blocked → Done | 150 |
| `SEC` | Security | Kanban | **no** | To Do → In Progress → Done | 80 |

1,201 in-scope issues total (1,200 plus the A31 Program), spread over the 12 months before the fixed reference date
(`2026-09-01T00:00:00Z`), each project mixing Story/Task/Bug/Sub-task plus a handful of Epics with
parent links. Ids and per-project key numbers are assigned in one global chronological pass
(mirroring Jira's own instance-wide sequential numeric id), so `FLO-1` is older than `FLO-2` and
both are older than any issue with a higher numeric id than theirs, project boundaries aside — except FLO-401, the A31 Program:
the highest id, yet created at the backfill start.

GTM's board configuration deliberately never maps the `Waiting` status to a column, to exercise
the data profile's "unmapped statuses" case.

Every field the normalization layer (`.claude/docs/ingestion.md` §8, "Normalization") needs to
exercise is present and internally consistent — the changelog histories are *derived from the same
simulated event timeline* as each issue's current field values, never authored independently, so
they can never disagree:

- **Status transitions**, including a Blocked/Waiting excursion on some projects, ~5% reopens
  (Done → In Progress) — see `expected.json` `reopens.count` (whole-dataset, incl. the
  out-of-scope `SEC` project) and `reopens.inScopeCount` (the figure the data profile's own
  reopen count, computed only over this connection's in-scope `norm.*` rows, can actually match).
- **Sprint membership** (`customfield_10020`, `schema.custom` = `com.pyxis.greenhopper.jira:gh-sprint`)
  on the three Scrum projects: 2-week sprints spanning the backfill window plus one future sprint;
  ~20% of Scrum issues carry over into the next sprint (a direct ~20% draw gated on the issue's
  home sprint having already closed, not an emergent property of how long an issue's arc runs —
  see `expected.json` `sprints.carryOverCount`).
- **Story points** (`customfield_10016`) on every Scrum Story.
- **Rank** (`customfield_10019`, `gh-lexo-rank`) — the current value on `fields`, changes only in
  the changelog (never as a tracked interval, per the normalization plan).
- **Flagged** (`customfield_10021`, a checkbox-style option field) on ~5% of issues.
- **Team** (`customfield_10001`, `atlassian-team`) on ~30% of issues, stored as-is.
- **Original estimates** (`timetracking.originalEstimateSeconds`) on ~45% of issues.
- **Worklogs** on ~40% of in-scope issues (1–4 entries each).
- Labels, components (per-project pools) and reassignment history (0–2 assignee changes/issue).

30 users (`accountId`s), 4 Atlassian Teams, a fixed `cloudId`
(`b3f1a2c4-5d6e-4f7a-8b9c-0d1e2f3a4b5c`) and fixed reference/priority/resolution/issue-link-type
catalogs. All of this is dumped, with exact counts, into `jira/expected.json` — that file is the
single source of truth the server's integration tests assert against; don't hand-copy numbers out
of this README into a test.

### The `jira-day2` scenario

A WireMock scenario (`Started` → `day2`, one simulated day of wall-clock time) exercises the
RECONCILE and incremental-sync paths:

- **One deleted issue** (`expected.json` → `day2.deletedIssueId`): present and 200 in `Started`,
  absent from every `search/jql` result and 404 on `GET /issue/{id}` in `day2`.
- **One moved issue** (`day2.movedIssueId`): in scope (e.g. `OPS`) in `Started`; in `day2` it's
  gone from `OPS`'s search results and `GET /issue/{id}` now reports it under the out-of-scope
  `SEC` project — the "found but a different project" reconcile case.
- **A handful of updated issues** (`day2.updatedIssueIds`): a status or story-points change dated
  at `day2Date` (`2026-09-02T00:00:00Z`), with a corresponding new changelog history entry and a
  bumped `updated` timestamp, so the ISSUES stream's page-diff can detect them.
- **Worklog feed deltas**: `worklog/updated`/`worklog/deleted` are empty in `Started` (any `since`
  value); in `day2` they report 2 new in-scope worklogs, 2 worklogs on **out-of-scope** `SEC`
  issues (the A1 filtering test — the client must fetch these via `worklog/list` and then drop them
  because their `issueId` isn't in `jira_raw_issues`), and one deleted in-scope worklog.

Switch scenario state directly against the running stub's WireMock admin API:

```
curl -X PUT http://localhost:8094/__admin/scenarios/jira-day2/state -H 'Content-Type: application/json' -d '{"state":"day2"}'
```

(Integration tests do this against the in-JVM WireMock instance instead of over HTTP.)

## The stub contract — what the client (commits 4–7) must match exactly

The stub lives at `jira-stub/{mappings,__files}` (standard WireMock: each `mappings/*.json` names
a `bodyFileName` in `__files/`). It's mounted read-only into the `jira-stub` compose service
(`docker-compose.yaml`, image `wiremock/wiremock:3.13.2`, port `127.0.0.1:8094`, same
digest-pinning style as Lettuce's `teams-stub`).

- **Gateway shape.** Every authenticated endpoint is served under
  `/ex/jira/{cloudId}/rest/...` (`cloudId` = `b3f1a2c4-5d6e-4f7a-8b9c-0d1e2f3a4b5c`, fixed). The one
  unauthenticated endpoint is `GET /_edge/tenant_info` → `{"cloudId": "..."}`. `jira.stubBaseUrl`
  (dev-only) is expected to reroute **both** the tenant_info host and the gateway host to this one
  stub instance — there's no separate fake `*.atlassian.net` origin to resolve.
- **Auth.** Any `Authorization: Basic ...` or `Authorization: Bearer ...` header is accepted (the
  stub does not validate credentials — the sample connection can use literally any email/token
  pair). A missing or malformed header gets a real `401` with a Jira-shaped error body, on
  **every** endpoint except `tenant_info`.
- **Pagination.**
  - `startAt`-paged endpoints (`statuses/search`, `users/search`, `issue/{id}/changelog`,
    `issue/{id}/worklog`, agile `board`, `board/{id}/sprint`): the first page matches whether the
    client sends no `startAt` at all or an explicit `startAt=0`; every later page requires an
    exact `startAt` match. Page sizes are the stub's own choice (deliberately smaller than what a
    real client would request, e.g. 3 per page for per-issue changelog/worklog, so pagination is
    actually exercised for issues with more than a handful of entries) — honour `startAt`/`total`
    from the response, don't assume a fixed page size.
  - `search/jql` is `nextPageToken`-paged (GET, per the real API): the first page has no
    `nextPageToken`, later pages require the exact opaque token the previous page returned
    (`"<Scenario>-page-N"`). **The stub ignores JQL text entirely** — project/date scoping is
    baked into the fixed response set, keyed only by the `fields` query parameter and the
    scenario. There are exactly two `fields` variants: `fields=*all,-comment,-worklog,-description,-attachment,-subtasks,-environment` (the ISSUES stream's
    full-field search: every field minus the six the raw store drops; the stub's documents carry none of them) and `fields=id` (the reconcile id-sweep and the Test-connection probe, a single page up to 5000 ids). A
    search with no `fields` matches nothing: real `search/jql` returns only `id` then, unlike the retired `/search`.
  - `changelog/bulkfetch` chunks are **ascending, exact-order** 50-id batches
    (`equalToJson` with `ignoreArrayOrder: false`) — see `expected.json` →
    `changelog.bulkfetchChunkCount`/`bulkfetchChunkSize`. **Chunk index 5 is deliberately
    unmapped** (`changelog.omittedBulkfetchChunkIndex`, its issue ids in
    `changelog.omittedBulkfetchChunkIssueIds`): a request for that exact chunk gets WireMock's
    default 404, which is the fallback trigger — the client must fall back to per-issue
    `GET /issue/{id}/changelog` for **exactly** those ids (and only those; every other chunk has a
    real mapping). `worklog/list` chunks use `ignoreArrayOrder: true` instead (order doesn't
    matter there) and are sized up to 1000 ids.
- **`issue/{id}` is stubbed only for the ids the pipeline actually calls it for** — the reconcile
  probe issue, and the deleted/moved day-2 issues (both scenario states) — because that endpoint
  is only ever called for a handful of anomalies (reconcile) or a single probe (Test connection),
  never for the whole issue set (full issue documents come from `search/jql`). Don't expect a
  mapping for an arbitrary in-scope issue id.
- **Catch-alls.** `issue/{id}/changelog` and `issue/{id}/worklog` have a generic low-priority
  "empty page" stub for issues with no real data, so the WORKLOGS/CHANGELOGS streams' backfill
  pass (which calls every in-scope issue) always gets a `200`, not a `404`, for the majority that
  simply have nothing to report.
- **`field/search`** (the optional Test-connection `field_search` probe only, `field-search`): one fixed page (`startAt` 0, `maxResults` 1,
  `isLast: false`, the first field) whose `total` equals the length of the `field` array, whatever the query asks.
- **`projects/fields`** (experimental, the optional `PROJECT_FIELDS` step): startAt-paged, 50 rows per page, one row
  per (field, work type) of each IN-SCOPE project (`projects-fields-<KEY>-page-N`). Matched on `urlPath` plus the
  `projectId` query parameter only — like `search/jql` ignores JQL, the stub ignores the repeated `workTypeId` params and
  answers every work type of the project. System fields plus the custom fields the dataset's issues use; the Kanban
  project's scheme leaves out Sprint and Story point estimate; the epic start date applies to the Epic work type only and Sprint
  to the non-epic work types, so the epic/task split is exercised.
- **Epic workflow.** `project/{key}/statuses` answers a workflow per issue type: the Epic entry is the project's workflow
  plus an epic-only `On Hold` status (id `10005`, in `statuses/search` too) before `Done`; no issue ever transitions into it,
  so no interval, digest or `expected.json` figure moves.
- **Reference data (`field`, `statuscategory`, `project/search`, `project/{key}/statuses`,
  `issuetype`, `resolution/search`, `issueLinkType`, `board/{id}/configuration`)
  is scenario-independent** — it does not change between `Started` and `day2`. (The stub still serves
  `priority/search`, but Flow has not called it since 2026-10-08; see `.claude/docs/jira-integration.md`.) Only issues,
  changelog, worklogs and the two `search/jql` variants are scenario-gated.
  `statuses/search` serves `statusCategory` as the real string enum (`"TODO"`/`"IN_PROGRESS"`/`"DONE"`, `statusSearchJson`),
  while issue payloads and project statuses keep the object form (`statusJson`); `.claude/docs/jira-integration.md` "Status category shapes".

### Timestamp formats

The stub deliberately emits **two different timestamp shapes**, matching what the two real Jira
Cloud APIs actually return — a real-tenant blocker discovered in phase 2:
`java.time.Instant.parse` only accepts strict ISO-8601 (`Z` or a colon-delimited `+HH:MM` offset)
and REJECTS the form the REST API v3 actually uses
(`Instant.parse("2024-01-15T10:20:30.123+0000")` throws `... could not be parsed at index 23`).

- **REST API v3** (`generate.mjs`'s `restIso(ms)`) — `yyyy-MM-dd'T'HH:mm:ss.SSS+0000` (a colonless
  offset, never a bare `Z`): an issue's own `created`/`updated`/`resolutiondate`, a changelog
  history's `created`, and a worklog's `started`/`created`/`updated`.
- **`changelog/bulkfetch`** — a history's `created` as epoch MILLIS (a JSON number), as the real endpoint returns
  it; the per-issue changelog pages (the omitted chunk's fallback) keep the REST API v3 text form.
- **Agile API** (`generate.mjs`'s `iso(ms)`, ordinary `toISOString()`) — `yyyy-MM-ddTHH:mm:ss.SSSZ`:
  a sprint's own `startDate`/`endDate`/`completeDate`, both on `GET board/{id}/sprint`'s response
  and the identically-named dates Jira duplicates onto an issue's own Sprint custom-field array
  (the latter isn't read by any Kotlin parser today — `JiraNormalizer.normalizeIssue` only reads
  that array's `id`/`name` — kept as `Z` anyway since it's the same sprint-owned date, sourced from
  the same Agile-API convention).

`server/src/main/kotlin/jira/JiraTime.kt`'s `parseJiraInstant`/`parseJiraInstantEpochMillis` is the
ONE parser every Jira-sourced timestamp in the server goes through — it accepts both shapes above
(plus a bare `+HH:MM`/`-HH:MM` offset) — see `.claude/docs/jira-integration.md` "Timestamps". Never
call `Instant.parse` directly on Jira-sourced text; never reintroduce a hand-rolled `iso()` call at
one of the REST-API call sites above.

## The hostile host (`jira/hostile.mjs`) — the worker-heap measurement

`jira/hostile.mjs` emulates a Jira host behind the allow-list that answers with the densest document the node ceiling lets
through (`.claude/docs/jira-integration.md` "Node and depth ceiling"): `search/jql` pages (a `nextPageToken` chain,
`Hostile-page-N`) and `GET /field` bodies carrying padding of the shape `"a":[{"a":0},{"a":0},...]` sized to just under
`maxResponseBytes / 8` structural tokens (1,048,576 at the default 8 MiB, ~2.8 MiB on the wire, ~108 MiB of parsed tree: the 112 B a node `JiraHeapFit.TREE_BYTES_PER_NODE` budgets). The pages
pass the ISSUES stream's typed reads, so a SYNC runs the whole way and a heap profile sees the real retention. Deterministic (no
randomness, no clock), zero dependencies; it never writes the committed `jira-stub/` (an `--out` whose `jira-stub` resolves to `sample-data/jira-stub`, symlinks included, is refused).

```
node sample-data/jira/generate.mjs --out /tmp/flow-jira-hostile                      # the normal stub (scale 1) ...
node sample-data/jira/hostile.mjs  --out /tmp/flow-jira-hostile --overlay --pages 20  # ... with the hostile endpoints layered over it
node sample-data/jira/hostile.mjs  --out /tmp/flow-jira-hostile --check               # re-verify the written bodies
node --test sample-data/jira/hostile.test.mjs                                          # the generator's own self-test (CI e2e-static, gates.sh)
```

WireMock mounts ONE directory, so layering is a file overlay: `--overlay` removes only the normal mappings the hostile ones
supersede (`search/jql` with the ISSUES `fields`, and `GET /field`), keeps every other endpoint (reference data, changelog, worklogs,
boards), and builds the hostile issue and field list on the normal stub's own first issue and field list. Without `--overlay` only
the hostile endpoints exist (the response path, not a whole SYNC). Other flags: `--pad page` puts the padding at the top level of
each page (built, then dropped by the typed decode) instead of inside the issue (retained with it, the worst case, the default);
`--max-response-bytes B` re-aims the padding when the target runs a raised `JIRA_MAX_RESPONSE_BYTES`. Every emitted body is
re-read and verified (valid JSON, tokens under the ceiling, bytes under the cap, depth under 512) before the script exits.

**The stored-size ceilings (`--pad history|worklog`, `--stored-bytes B`).** The raw writers refuse an item over a stored-size ceiling
(`.claude/docs/jira-integration.md` "Stored-size ceilings": 512 KiB a history, 16 KiB a worklog, `jira.maxStoredPayloadBytes` an issue or
entity), so to measure the stored-text paths (PROCESS pages, the per-item history/worklog parse) the padded item must be one the ceiling lets
through, and to see the refusal one it does not. `--pad history` makes the search pages carry a PLAIN hostile issue and answers
`POST changelog/bulkfetch` for the hostile issue ids (any batch naming a `9xxxxx` id) with one dense history per issue, as many as fit under the byte
cap and the node ceiling, the padding being `historyMetadata.a`, a key the raw trim keeps; `--pad worklog` answers `GET issue/{id}/worklog` for
each hostile issue with one dense worklog whose padding is `properties`. `--stored-bytes B` aims the padded item's own JSON text at B bytes (never over,
within 8 bytes; the stored canonical text is within a few bytes of it) so a run can land just under or just over a ceiling: the defaults are
500000 for a history and 15000 for a worklog (just under); with `--pad issue|page` it replaces "just under the node ceiling" for the page
and the `GET /field` entity. With `--overlay`, `--pad history|worklog` keep the normal `GET /field` mapping (the field list is not the subject).
A batch that mixes a normal issue with a hostile one gets no normal history in the hostile answer: a measurement stub, not a whole SYNC.

Run it on the **flow-perf** stack ONLY, never the dev stack (`docker-compose.perf.yaml` mounts `$FLOW_PERF_STUB_DIR/jira-stub`
into the stub; `.claude/docs/metrics.md` "Performance (scale 20)"):

```
FLOW_PERF_STUB_DIR=/tmp/flow-jira-hostile \
  docker compose -p flow-perf -f docker-compose.yaml -f docker-compose.perf.yaml up --build -d
# point the perf stack's data source at the stub as for any perf run, trigger a SYNC, watch the worker heap
docker compose -p flow-perf -f docker-compose.yaml -f docker-compose.perf.yaml down -v
```

A worker whose `-Xmx` cannot hold `ingest.workerSlots` such trees now refuses to start (`jira/JiraHeapFit.kt`); to measure past the
check, give the worker the heap it asks for (its error names the `-Xmx`) or lower the slots, then raise them to find the real limit.

## Size

`jira-stub/` is ~13 MiB (801 mapping/body file pairs), comfortably under the ~15 MB guideline —
the bulk of it is the `search/jql` full-field pages (12-13 pages × 2 scenarios, ~215 KiB each,
1,201 issues' worth of `fields` documents). If it needs to shrink further, the first lever is
trimming fields from `issueFieldsJson()` in `generate.mjs`, not the issue count (the counts above
are load-bearing for the "~1,200 issues" dataset shape the plan calls for).

# GitLab stub — a synthetic self-managed GitLab + WireMock

`gitlab/generate.mjs` builds a deterministic, zero-dependency **self-managed GitLab** world (REST API v4 plus `POST /api/graphql`) and the
WireMock stub that serves it, the way `jira/generate.mjs` does for Jira. It is the contract the GitLab connector PRs code against
(`.claude/docs/gitlab-integration.md`); nothing in the app reads it yet. The same mappings are served by the compose `gitlab-stub`
(`127.0.0.1:8095`) and the in-JVM `GitLabStubServer` (`server/src/test/kotlin/GitLabStubServer.kt`), and the ground truth tests assert is
`gitlab/expected.json`.

## Regenerating

```
node sample-data/gitlab/generate.mjs [--users N] [--projects N] [--months N] [--out DIR]
```

Node >=24, no npm install. With **no flags** the output is the committed default world and is byte-identical across runs (seeded mulberry32
streams, one per concern; the "current time" is the frozen `2026-09-01T00:00:00Z`, never `Date.now()`). Commit `gitlab-stub/` and
`gitlab/expected.json`: they are build artifacts, not hand-edited. The guard is a self-test, run by `scripts/gates.sh e2e` and the CI `e2e-static` job:

```
node --test sample-data/gitlab/generate.test.mjs        # determinism, committed stub == a fresh run, invariants
# by hand, the same byte-identity check as for Jira:
node sample-data/gitlab/generate.mjs --out /tmp/a && node sample-data/gitlab/generate.mjs --out /tmp/b && diff -rq /tmp/a /tmp/b   # prints nothing
```

**Scale flags** build the performance world (never committed; `--out` is the way to keep it off the repo): `--users N` (GitLab humans, default 6, min 6),
`--projects N` (in-scope projects, default 4, min 4; the archived, out-of-scope and day-2-only projects always stay), `--months N` (history, default 6,
min 2). Commits grow with users x months (about 8 per person-month: 300 at the defaults), merge requests with users x months too (about 1.7), whatever the
project count: the density is fixed, so a bigger world is more people and months, never more items per person. Explicit
`--users 6 --projects 4 --months 6` equals no flags. `--users 70 --projects 200 --months 24` is 45,668 mappings, 27,791 bodies and 395 MiB in about 5.6 s: 14.2k
commits (~6.5 % merges), 2.8k merge requests, 23.3k notes and 72 users. WireMock serves it (startup ~50 s at `-Xmx1g`, ~10-20 ms for a matched request), but
matching is linear in the mapping count and the per-commit diff mappings dominate, so a world several times larger needs the stub's diff mappings collapsed
first. `docker-compose.perf.yaml` mounts such a world as the `flow-perf` stack's `gitlab-stub` (its header gives the command used for the performance runs).

A data source is configured with groups 7 and 9. Users: id 1 `flow-sync` (the **admin** the token belongs to, `is_admin`, not a bot); ids 2-7

## The endpoint contract

Every route is under `/api/v4` except GraphQL. **Auth:** a non-empty `PRIVATE-TOKEN` header or `Authorization: Bearer <non-empty>` is accepted (the value is never
checked); otherwise every `/api/...` path answers `401 {"message":"401 Unauthorized"}` (priority 1, so no endpoint needs its own check). **Pagination:** offset only, and
only `per_page=100` is mapped (another size falls through to `404 {"error":"404 Not Found"}`); page 1 matches `page` absent or `1` only, later pages need the exact `page`, and any other numeric `page` (past the end, or `0`) answers `[]` with the usual headers (`X-Page` echoing the request, empty `X-Next-Page`/`X-Prev-Page`, the list's real `X-Total`, a `first`/`last` `Link`).
Every list answers `X-Page`, `X-Per-Page`, `X-Next-Page` and `X-Prev-Page` (both empty at the ends), `X-Total`, `X-Total-Pages` (0 for an empty list) and a `Link`
header of absolute URLs (`rel` prev/next/first/last, built from the request's own base URL by WireMock response templating; they carry the match parameters, not
`since`/`updated_after`). Static `RateLimit-*` headers ride on every response. Extra query parameters a mapping does not name (`since`, `updated_after`, `order_by`
on groups' projects, ...) are ignored.

| Endpoint | Match and answer |
|---|---|
| `GET /version`, `GET /user`, `GET /personal_access_tokens/self` | the version; the admin user (`is_admin: true`); `scopes: ["read_api"]`, `active`, `expires_at` |
| `GET /groups/:id` | by numeric id or URL-encoded full path (`platform%2Ftooling`, either `%2F` case) for groups 7, 8, 9, 12 |
| `GET /groups/:id/projects` | `include_subgroups=true`, `archived=false` (live) or no `archived` (also the archived project), `per_page=100`, order by id |
| `GET /projects/:id` | by id or encoded path; the full project object (`namespace`, `default_branch`, `archived`, `path_with_namespace`) |
| `GET /projects/:id/repository/branches/:branch` | the default branch of each project (`master` for project 4) |
| `GET /users` | admin view (`email`, `bot`, `state`, `is_admin`, `commit_email`), `per_page=100`; `GET /users/:id/emails` the confirmed secondary emails (`[]` for most) |
| `GET /projects/:id/repository/commits` | `ref_name=<branch>` or `<sha>..<branch>`, `with_stats=true`, `per_page=100`, newest first in `git log` order; ranges for each project's **stored head** (a mainline commit ~80% in) and its **started tip** (empty at day zero) |
| `GET /projects/:id/repository/merge_base` | `refs[]=<sha>&refs[]=<branch or tip sha>` in either order, for the stored head and the started tip of each project; the commit object. Also, for project 1's five force-pushed commits (the base is the commit itself at day zero, the fork point after the force-push) and its divergence commit (always itself), `refs[]=<sha>&refs[]=<branch>` and `refs[]=<sha>&refs[]=<tip>`, plus the probe `refs[]=<tip>&refs[]=<branch>` (the tip itself): the re-list sweep's confirmations; any other pair is unmapped (404) |
| `GET /projects/:id/repository/commits/:sha/diff` | `per_page=100` (+`page`): `diff`, `new_path`, `old_path`, `a_mode`, `b_mode`, `new_file`, `renamed_file`, `deleted_file`, `generated_file`, and `too_large` / `collapsed` only on the files they apply to; sorted by path |
| `GET /groups/:id/merge_requests` | `scope=all`, `state=all`, `include_subgroups=true`, `order_by=updated_at`, `sort=desc` (newest first, GitLab's default `sort`), `per_page=100`; `updated_after` is ignored (the full set is always answered) |
| `GET /projects/:id/merge_requests/:iid` | the merge request object (the group listing's shape; RECONCILE's confirmation probe); a deleted or not-yet-existing one is `404 {"message":"404 Not found"}` |
| `GET /projects/:id/merge_requests/:iid/notes` | `sort=asc`, `order_by=created_at`, `per_page=100` (+`page`) |
| `GET /projects/:id/merge_requests/:iid/approvals`, `.../reviewers` | the legacy approvals object; `[{user, state, created_at}]` |
| `POST /api/graphql` | body contains the project `fullPath` and `diffStatsSummary`: every MR of that project as `{iid (string), diffStatsSummary {additions deletions fileCount}}` plus `pageInfo`; ONE MR (`expected.json` `mergeRequests.nullDiffStatsGap`) has `diffStatsSummary: null` and a top-level `errors` entry; an unknown project is `{"data":{"project":null}}` |

**404s** (JSON, priority 9): unknown project `{"message":"404 Project Not Found"}` (also for any sub-resource), group `404 Group Not Found`, user `404 User Not Found`, branch
`404 Branch Not Found`, commit `404 Commit Not Found`, merge request (any of its three sub-resources) `404 Not found`; any other `/api/...` path
`{"error":"404 Not Found"}`.

## The `gitlab-day2` scenario

A WireMock scenario (`Started` -> `day2`, one simulated day, `2026-09-02T00:00:00Z`), switched like Jira's:

```
curl -X PUT http://localhost:8095/__admin/scenarios/gitlab-day2/state -H 'Content-Type: application/json' -d '{"state":"day2"}'
```

(Tests use `GitLabStubServer.setScenarioState(GitLabStubServer.SCENARIO, GitLabStubServer.DAY2)` and `resetScenarios()`.) A response identical in both states is one ungated
mapping; the rest come in a `-started` and a `-day2` variant. The deltas, all recorded in `expected.json` `day2`:

- **Force-push (project 1):** its last five direct commits are rewritten (two squashed into one, one dropped, two rebased) and two brand-new commits follow. The head moves,
  the old commits are gone from the branch listing (their `/diff` still answers, as an unreachable commit does on a real server), and `merge_base(oldTip, branch)` returns
  the older divergence commit (`day2.forcePush.divergenceSha`). A stored head before the divergence stays an ancestor.
- **Branch rename (project 4):** `master` -> `main`: `default_branch`, the branch endpoint and the commit list move; `ref_name=master` and `branches/master` are 404. Two new commits.
- **Deleted MR (project 3, `day2.deletedMergeRequest`):** gone from the group list and the GraphQL nodes, 404 on notes/approvals/reviewers.
- **Moved project (project 2):** gone from the group 7 and 8 project lists; `GET /projects/2` answers `sandbox/build-kit` in group 12 (its MRs are listed under group 12 now).
- **New project (7, `platform/tooling/lint-rules`):** 404 at day zero; five commits and one merged MR in day2.
- **New commits and MR updates:** project 3 gets four direct commits and one open MR merged (a merge commit with a second parent); one open MR in project 1 gets
  "requested changes" and a comment; an open MR in project 4 is closed; a draft in project 3 is marked ready; two more get a comment.
