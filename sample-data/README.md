# Sample data — synthetic Jira Cloud dataset + WireMock stub

This directory holds a **deterministic, zero-dependency** synthetic Jira Cloud dataset and the
WireMock stub that serves it, generated by `jira/generate.mjs`. It exists so that:

- `docker compose up` gives you a Jira-shaped API to point a real connection at without touching
  the real Atlassian cloud (`jira-stub` in `docker-compose.yaml`, `127.0.0.1:8094`);
- the server's integration tests (Testcontainers + the in-JVM WireMock `JiraStubServer`, which
  serves this dataset to the Jira client and sync pipeline) get a fixed, richly-shaped dataset to assert
  exact counts against (`jira/expected.json`), instead of hand-authored fixtures that drift from
  what the real API actually returns.

## Regenerating

```
node sample-data/jira/generate.mjs [--scale N] [--out DIR]
```

Node ≥24, no npm install. With **neither flag**, the script is **fully deterministic**: every
random draw comes from a seeded PRNG (mulberry32, fixed seed) and the "current time" is a frozen
constant (`2026-09-01T00:00:00.000Z`, never `Date.now()`) — running it twice produces
byte-identical output in `jira-stub/` and `jira/expected.json`. Verified as part of this commit;
re-verify after any change to the generator:

```
node sample-data/jira/generate.mjs && cp -r sample-data/jira-stub /tmp/a && cp sample-data/jira/expected.json /tmp/a/
node sample-data/jira/generate.mjs && cp -r sample-data/jira-stub /tmp/b && cp sample-data/jira/expected.json /tmp/b/
diff -rq /tmp/a /tmp/b   # must print nothing
```

Re-run it whenever you change the generator, and commit both `jira-stub/` and `jira/expected.json`
— they are build artifacts of `generate.mjs`, not hand-edited.

**`--scale N`** multiplies every project's issue/epic counts by `N` (default 1 — the committed
dataset's own shape, ~1,200 in-scope issues; `N=20` is the phase-3 performance run's ~24k-issue
dataset, `.claude/docs/ingestion.md`'s perf check). It never touches sprint/user/team counts, ids,
chunking or the day2 scenario at the default `N=1` (`Math.round(x*1) === x` is a no-op).
**`--out DIR`** writes to `DIR/jira-stub` and `DIR/jira/expected.json` instead of this directory —
used by the scale-20 performance run so it never touches the committed dataset:

```
node sample-data/jira/generate.mjs --scale 20 --out /tmp/flow-jira-x20
```

Runs with either flag are not asserted byte-identical against anything (only the default,
no-flags invocation is); they still draw from the same deterministic PRNGs.

### Phase 3 (v0.3.0) additions

On top of the phase-2 shape described below, the generator also produces the inputs the `metrics`
layer (`.claude/docs/domain-model.md`) needs, added by a **second, independently-seeded PRNG
stream** (`rng2`, distinct from the phase-2 dataset's own `rng`) so none of phase-2's ids,
timelines, the omitted bulkfetch chunk or the day2 scenario shift:

- **Epic story points** (D7) — every epic (in and out of scope) carries its own `customfield_10016`
  value, 20–80.
- **Epic dates** — a "Start date" custom field (`customfield_10015`, `schema.custom`
  `…:datepicker`) and the system `duedate` field on every epic; ~25% of epics get one later date
  change in the changelog (`fieldId: "duedate"` or `customfield_10015`, picked per epic).
- **Parent moves** — ~3% of tasks/stories/bugs parented to an epic move to a different epic in the
  same project once, as a `{field: "Parent", fieldId: "parent"}` changelog item; the issue's
  current `fields.parent` always reflects the last move's target (`expected.json` →
  `parentMoves`).
- **Story-point changes after start** — on Scrum stories that have started (passed their first
  In Progress transition): ~15% get a story-point value change dated after that transition; a
  further ~5% are "estimated late" (no story points at the start, gaining their eventual value only
  via that later changelog entry) — see `expected.json` → `estimates.taskEstimateChangedAfterStartCount`/
  `taskEstimatedLateCount`.
- **Work category** (`customfield_10030`, `schema.custom` `…:select`, options "Product
  Development"/"Maintenance"/"Cost of Poor Quality") — every epic, and ~60% of every other issue
  (D8's task-else-epic fallback needs both populated).
- **Worklog `created`/`updated` skew** — ~20% of worklogs get `created` = `started` + 1–5 days
  (instead of `created == started`); a further, independent ~10% get `updated` set later than
  `created` (report 14's late-logging measure).
- **Sprint `completeDate` skew** — ~30% of closed sprints get `completeDate` = `endDate` + 0–2 days
  instead of exactly `endDate`.
- **A future-sprint backlog** — ~10 estimated Scrum stories are placed (or reset, if not already
  never-started — see the code comment in `generate.mjs`) into their project's one future sprint,
  as a never-started TODO issue: D9's "future sprints count as backlog too" case, as opposed to a
  genuinely unscheduled backlog item.
- **A deterministic 30-user roster** over the 4 Atlassian Teams (2 users left on no team),
  `expected.json` → `teams.roster` — the source data for D1's dated team membership, entered
  through the metrics-config API in a later commit (phase-3 plan §2 decision 6).
- **Two golden fixtures**, computed by the generator from its own simulated timeline (never
  hand-authored) — `expected.json` → `golden.sprint` (one closed FLO sprint's committed/added/
  removed/final/delivered/carried-over/dropped MD and item counts, grace 0, 1 SP = 1 MD) and
  `golden.epic` (one FLO epic's own budget, start/due dates and child-SP sum) — the same
  "independent second implementation" precedent as `EXPECTED_STATUS_CATEGORY`
  (`.claude/docs/testing.md`), for a later commit's derivation-kernel tests to compare against.

These additions grow `changelog.inScopeHistories`/`allProjectsHistories` (new changelog entries)
but leave every other phase-2 figure — issue ids and counts, the omitted bulkfetch chunk, the day2
scenario, `worklogs.inScopeCount`/`inScopeIssueCount`, `reopens`, `sprints.carryOverCount` — bit
for bit unchanged (phase-3 plan §0 A2).

## The dataset

Four Jira projects the sample connection's `projectKeys` cover, plus a fifth that is deliberately
**out of scope** (to test that the client never requests its issues, yet still has to filter its
worklogs out of the instance-wide worklog feed — see "A1" in the ingestion plan):

| Key | Name | Board | In scope | Workflow | Issues |
|---|---|---|---|---|---|
| `FLO` | Flow Core | Scrum | yes | To Do → In Progress → In Review → Done | 400 |
| `PLT` | Platform | Scrum | yes | To Do → In Progress → **Blocked** → In Review → Done | 350 |
| `GTM` | Go To Market | Scrum | yes | To Do → In Progress → In Review → **Waiting** → Done | 300 |
| `OPS` | Operations | Kanban | yes | To Do → In Progress → Blocked → Done | 150 |
| `SEC` | Security | Kanban | **no** | To Do → In Progress → Done | 80 |

1,200 in-scope issues total, spread over the 12 months before the fixed reference date
(`2026-09-01T00:00:00Z`), each project mixing Story/Task/Bug/Sub-task plus a handful of Epics with
parent links. Ids and per-project key numbers are assigned in one global chronological pass
(mirroring Jira's own instance-wide sequential numeric id), so `FLO-1` is older than `FLO-2` and
both are older than any issue with a higher numeric id than theirs, project boundaries aside.

GTM's board configuration deliberately never maps the `Waiting` status to a column, to exercise
the data profile's "unmapped statuses" case.

Every field the normalization layer (`.claude/docs/ingestion.md` §8, "Normalization") needs to
exercise is present and internally consistent — the changelog histories are *derived from the same
simulated event timeline* as each issue's current field values, never authored independently, so
they can never disagree:

- **Status transitions**, including a Blocked/Waiting excursion on some projects, ~5% reopens
  (Done → In Progress) — see `expected.json` `reopens.count` (whole-dataset, incl. the
  out-of-scope `SEC` project) and `reopens.inScopeCount` (the figure the data profile's own
  reopen count, computed only over this connection's in-scope `norm.*` rows, can actually match).
- **Sprint membership** (`customfield_10020`, `schema.custom` = `com.pyxis.greenhopper.jira:gh-sprint`)
  on the three Scrum projects: 2-week sprints spanning the backfill window plus one future sprint;
  ~20% of Scrum issues carry over into the next sprint (a direct ~20% draw gated on the issue's
  home sprint having already closed, not an emergent property of how long an issue's arc runs —
  see `expected.json` `sprints.carryOverCount`).
- **Story points** (`customfield_10016`) on every Scrum Story.
- **Rank** (`customfield_10019`, `gh-lexo-rank`) — the current value on `fields`, changes only in
  the changelog (never as a tracked interval, per the normalization plan).
- **Flagged** (`customfield_10021`, a checkbox-style option field) on ~5% of issues.
- **Team** (`customfield_10001`, `atlassian-team`) on ~30% of issues, stored as-is.
- **Original estimates** (`timetracking.originalEstimateSeconds`) on ~45% of issues.
- **Worklogs** on ~40% of in-scope issues (1–4 entries each).
- Labels, components (per-project pools) and reassignment history (0–2 assignee changes/issue).

30 users (`accountId`s), 4 Atlassian Teams, a fixed `cloudId`
(`b3f1a2c4-5d6e-4f7a-8b9c-0d1e2f3a4b5c`) and fixed reference/priority/resolution/issue-link-type
catalogs. All of this is dumped, with exact counts, into `jira/expected.json` — that file is the
single source of truth the server's integration tests assert against; don't hand-copy numbers out
of this README into a test.

### The `jira-day2` scenario

A WireMock scenario (`Started` → `day2`, one simulated day of wall-clock time) exercises the
RECONCILE and incremental-sync paths:

- **One deleted issue** (`expected.json` → `day2.deletedIssueId`): present and 200 in `Started`,
  absent from every `search/jql` result and 404 on `GET /issue/{id}` in `day2`.
- **One moved issue** (`day2.movedIssueId`): in scope (e.g. `OPS`) in `Started`; in `day2` it's
  gone from `OPS`'s search results and `GET /issue/{id}` now reports it under the out-of-scope
  `SEC` project — the "found but a different project" reconcile case.
- **A handful of updated issues** (`day2.updatedIssueIds`): a status or story-points change dated
  at `day2Date` (`2026-09-02T00:00:00Z`), with a corresponding new changelog history entry and a
  bumped `updated` timestamp, so the ISSUES stream's page-diff can detect them.
- **Worklog feed deltas**: `worklog/updated`/`worklog/deleted` are empty in `Started` (any `since`
  value); in `day2` they report 2 new in-scope worklogs, 2 worklogs on **out-of-scope** `SEC`
  issues (the A1 filtering test — the client must fetch these via `worklog/list` and then drop them
  because their `issueId` isn't in `jira_raw_issues`), and one deleted in-scope worklog.

Switch scenario state directly against the running stub's WireMock admin API:

```
curl -X PUT http://localhost:8094/__admin/scenarios/jira-day2/state -H 'Content-Type: application/json' -d '{"state":"day2"}'
```

(Integration tests do this against the in-JVM WireMock instance instead of over HTTP.)

## The stub contract — what the client (commits 4–7) must match exactly

The stub lives at `jira-stub/{mappings,__files}` (standard WireMock: each `mappings/*.json` names
a `bodyFileName` in `__files/`). It's mounted read-only into the `jira-stub` compose service
(`docker-compose.yaml`, image `wiremock/wiremock:3.13.2`, port `127.0.0.1:8094`, same
digest-pinning style as Lettuce's `teams-stub`).

- **Gateway shape.** Every authenticated endpoint is served under
  `/ex/jira/{cloudId}/rest/...` (`cloudId` = `b3f1a2c4-5d6e-4f7a-8b9c-0d1e2f3a4b5c`, fixed). The one
  unauthenticated endpoint is `GET /_edge/tenant_info` → `{"cloudId": "..."}`. `jira.stubBaseUrl`
  (dev-only) is expected to reroute **both** the tenant_info host and the gateway host to this one
  stub instance — there's no separate fake `*.atlassian.net` origin to resolve.
- **Auth.** Any `Authorization: Basic ...` or `Authorization: Bearer ...` header is accepted (the
  stub does not validate credentials — the sample connection can use literally any email/token
  pair). A missing or malformed header gets a real `401` with a Jira-shaped error body, on
  **every** endpoint except `tenant_info`.
- **Pagination.**
  - `startAt`-paged endpoints (`statuses/search`, `users/search`, `issue/{id}/changelog`,
    `issue/{id}/worklog`, agile `board`, `board/{id}/sprint`): the first page matches whether the
    client sends no `startAt` at all or an explicit `startAt=0`; every later page requires an
    exact `startAt` match. Page sizes are the stub's own choice (deliberately smaller than what a
    real client would request, e.g. 3 per page for per-issue changelog/worklog, so pagination is
    actually exercised for issues with more than a handful of entries) — honour `startAt`/`total`
    from the response, don't assume a fixed page size.
  - `search/jql` is `nextPageToken`-paged (GET, per the real API): the first page has no
    `nextPageToken`, later pages require the exact opaque token the previous page returned
    (`"<Scenario>-page-N"`). **The stub ignores JQL text entirely** — project/date scoping is
    baked into the fixed response set, keyed only by the `fields` query parameter and the
    scenario. There are exactly two `fields` variants: no `fields` param at all (the default,
    full-field search) and `fields=id` (the reconcile id-sweep, a single page up to 5000 ids).
  - `changelog/bulkfetch` chunks are **ascending, exact-order** 50-id batches
    (`equalToJson` with `ignoreArrayOrder: false`) — see `expected.json` →
    `changelog.bulkfetchChunkCount`/`bulkfetchChunkSize`. **Chunk index 5 is deliberately
    unmapped** (`changelog.omittedBulkfetchChunkIndex`, its issue ids in
    `changelog.omittedBulkfetchChunkIssueIds`): a request for that exact chunk gets WireMock's
    default 404, which is the fallback trigger — the client must fall back to per-issue
    `GET /issue/{id}/changelog` for **exactly** those ids (and only those; every other chunk has a
    real mapping). `worklog/list` chunks use `ignoreArrayOrder: true` instead (order doesn't
    matter there) and are sized up to 1000 ids.
- **`issue/{id}` is stubbed only for the ids the pipeline actually calls it for** — the reconcile
  probe issue, and the deleted/moved day-2 issues (both scenario states) — because that endpoint
  is only ever called for a handful of anomalies (reconcile) or a single probe (Test connection),
  never for the whole issue set (full issue documents come from `search/jql`). Don't expect a
  mapping for an arbitrary in-scope issue id.
- **Catch-alls.** `issue/{id}/changelog` and `issue/{id}/worklog` have a generic low-priority
  "empty page" stub for issues with no real data, so the WORKLOGS/CHANGELOGS streams' backfill
  pass (which calls every in-scope issue) always gets a `200`, not a `404`, for the majority that
  simply have nothing to report.
- **Reference data (`field`, `statuscategory`, `project/search`, `project/{key}/statuses`,
  `issuetype`, `priority/search`, `resolution/search`, `issueLinkType`, `board/{id}/configuration`)
  is scenario-independent** — it does not change between `Started` and `day2`. Only issues,
  changelog, worklogs and the two `search/jql` variants are scenario-gated.

### Timestamp formats

The stub deliberately emits **two different timestamp shapes**, matching what the two real Jira
Cloud APIs actually return — a real-tenant blocker discovered in phase 2:
`java.time.Instant.parse` only accepts strict ISO-8601 (`Z` or a colon-delimited `+HH:MM` offset)
and REJECTS the form the REST API v3 actually uses
(`Instant.parse("2024-01-15T10:20:30.123+0000")` throws `... could not be parsed at index 23`).

- **REST API v3** (`generate.mjs`'s `restIso(ms)`) — `yyyy-MM-dd'T'HH:mm:ss.SSS+0000` (a colonless
  offset, never a bare `Z`): an issue's own `created`/`updated`/`resolutiondate`, a changelog
  history's `created`, and a worklog's `started`/`created`/`updated`.
- **Agile API** (`generate.mjs`'s `iso(ms)`, ordinary `toISOString()`) — `yyyy-MM-ddTHH:mm:ss.SSSZ`:
  a sprint's own `startDate`/`endDate`/`completeDate`, both on `GET board/{id}/sprint`'s response
  and the identically-named dates Jira duplicates onto an issue's own Sprint custom-field array
  (the latter isn't read by any Kotlin parser today — `JiraNormalizer.normalizeIssue` only reads
  that array's `id`/`name` — kept as `Z` anyway since it's the same sprint-owned date, sourced from
  the same Agile-API convention).

`server/src/main/kotlin/jira/JiraTime.kt`'s `parseJiraInstant`/`parseJiraInstantEpochMillis` is the
ONE parser every Jira-sourced timestamp in the server goes through — it accepts both shapes above
(plus a bare `+HH:MM`/`-HH:MM` offset) — see `.claude/docs/jira-integration.md` "Timestamps". Never
call `Instant.parse` directly on Jira-sourced text; never reintroduce a hand-rolled `iso()` call at
one of the REST-API call sites above.

## Size

`jira-stub/` is ~13 MiB (782 mapping/body file pairs), comfortably under the ~15 MB guideline —
the bulk of it is the `search/jql` full-field pages (12 pages × 2 scenarios, ~215 KiB each,
1,200 issues' worth of `fields` documents). If it needs to shrink further, the first lever is
trimming fields from `issueFieldsJson()` in `generate.mjs`, not the issue count (the counts above
are load-bearing for the "~1,200 issues" dataset shape the plan calls for).
